# EETB 项目介绍与基本原则

> 项目名称：**EETB（Earthquake Engineering Toolbox，暂定释义）**  
> 当前子项目：**GMTools（Ground Motion Tools）**  
> 文档类型：项目定位与长期约束  
> 状态：初版设计基线，后续修改应以明确的需求为依据

## 1. 项目背景与目标

地震工程与地震学领域存在多种地震动记录格式：SAC、miniSEED、PEER、COSMOS/SMC、K-NET/KiK-net、常见 TXT/CSV，以及机构或仪器自定义格式。即使同为文本文件，也可能使用单列时程、多列连续采样、时间—幅值两列或多通道数据列等不同组织方式。使用者往往需要额外软件或编写脚本才能转换与核查。

EETB 定位为可逐步扩展的地震工程工具集；**GMTools 是其首个子工具，聚焦地震动记录的读取、解释、转换与可视化核查**。现阶段优先解决不同来源记录的格式互操作，不追求一次性覆盖完整的地震动分析功能。

GMTools 的基本使用流程为：

**选择一个输入文件 → 解析其中的独立通道 → 检查或补充必要参数 → 每个通道分别输出一个目标文件。**

### 1.1 面向的典型场景

- 下载了 SAC、miniSEED 或 PEER 等格式的地震动，需要转换为另一个程序能够读取的单通道文件。
- 拿到没有标准表头的 TXT/CSV，希望通过指定起始行、列和时间信息解释为时程。
- 原始文件包含多个通道，需要在界面中同时预览，并分别导出为单通道文件。
- 需要以 GUI 完成偶发转换，或以 CLI 在脚本中重复执行相同规则；后续可以扩展到多个输入文件的独立批量转换。

## 2. 项目组织与边界

```text
EETB/
└── GMTools/
```

- **EETB**：项目容器及未来地震工程相关工具的归属，不强制当前构建一个大型综合应用。
- **GMTools**：能够独立构建、运行和维护的地震动工具；CLI、GUI 共享其核心处理代码。
- **REST**：独立的结构监测及分析项目。GMTools 可以复用成熟的方法、算法或具有许可兼容性的代码，但不以 REST 的数据集、工作流和应用架构为依赖。

本项目不是地震动数据库管理系统，也不是 REST 的附属数据导入模块。功能取舍首先服务于**可靠且简便的文件转换**。

## 3. 不可轻易改变的设计原则

### P1. 输入以单个文件为边界

- 每次读取处理**一个文件的原始字节内容**，按指定或识别出的格式交给匹配的 Reader。
- 一个输入文件可解析出 1 条或多条 Trace；不限定最多三个通道。
- **不在读取阶段跨多个文件关联或合并分量**，不识别目录中的“同台站三分量组合”。未来批量功能也首先是对各文件分别执行相同转换。
- 文件扩展名仅用于辅助识别，不能作为唯一判据；自动检测不可靠时可手动指定格式。

### P2. 以单通道时程为独立数据基本单元

- 核心数据模型为 `FileData`（一个文件的解析结果）与 `Trace`（一条独立通道的时程）。
- 每个 `Trace` 独立保存样本、采样信息、物理量、单位、通道标识及必要元信息；不依赖其他 Trace 的共同属性。
- 样本数量由样本数组决定，时长由采样信息计算，不维护重复且可能互相矛盾的字段。
- 多通道仅表现为一个 `FileData` 内多条 Trace；不额外引入 Ground Motion、Record Set 或结构监测式数据集层级。
- 常见地震动是 1～3 分量，但不因此在代码中固定三个通道。

### P3. 输出以单个 Trace、单个文件为边界

- 一个 Writer 每次接收一条 Trace，生成一个目标文件。
- 输入文件存在多个通道时，默认导出所有通道，逐通道生成多个文件；GUI/CLI 可以选择部分通道。
- **即使某种目标格式支持多通道，本项目首期也不提供多通道写入或跨文件汇总输出。**
- 统一处理文件名冲突、非法通道名和已有文件覆盖；默认不静默覆盖。

### P4. 标准文本和通用文本共享基础数值解析能力

- TXT、DAT、CSV、PEER AT2 等文本文件先进行文本解码，再进入通用数值解析流程。
- 通用解析的核心是：数据从第几行开始、如何分隔、按行连续展开还是按列构成通道、是否存在时间列、哪些列为数据列。
- **标准格式不是另一个完整的文本解析体系**：标准格式规则负责识别表头、提取元数据并生成通用解析参数；有真正的特殊数据段时再添加少量专门逻辑。
- 不追求靠猜测自动解释所有非标准文件。模糊情形应允许用户查看原文、修改规则并确认解析结果。

### P5. 基础数据模型稳定，格式特有信息可扩展

- 基础 Trace 只保留跨格式普遍有效的字段。
- SAC、PEER、miniSEED 等专有元信息通过组合式 `Metadata`/扩展属性保存；不为每种格式引入 `SACTrace` 等继承类型。
- 扩展信息可以保存在文件级或通道级，以匹配信息的真实归属；不必强行把每种格式所有头段字段映射到统一固定结构。
- Reader 和 Writer **彼此独立**；某一专用格式可以只支持读取，不必为了接口对称而实现写入。
- 转换到信息容量较小的格式时，允许明确报告元数据无法保留，但不能宣称无损转换。

### P6. 不猜测物理含义，不静默处理波形

- 不把未知单位、未知采样间隔或数字计数值当作已知加速度。
- 当信息不完整时允许读取和预览，但**按照目标格式的真实要求验证能否导出**。
- 文件标定系数、物理单位转换和用户主动调幅是不同操作，必须分开处理。
- 第一批加速度单位预设为 `g`、`m/s²`、`cm/s²`（Gal），采用标准换算 `1 g = 9.80665 m/s² = 980.665 cm/s²`。
- 默认保留导入后的时程数值与原始单位；仅在目标要求或用户明确选择时转换单位。不得自动滤波、去趋势、积分、重采样、截取、对齐或调幅。
- 文本头段与实际数据冲突时，应报告诊断信息，不自动截断或补造样本。

### P7. 方便核查，但保持简单

- **CLI**：少量直观命令，优先支持 `info`、`convert`、`formats`；正常文件一条命令完成转换。复杂文本规则通过可复用配置传入。
- **GUI**：围绕“导入文件—检查数据与参数—预览全部通道—导出”设计单窗口使用流程。标准文件应尽可能无需手动配置；复杂文本提供类似 SeismoSignal 的原始文本预览、布局选择和参数输入。
- 自动解析出来的字段应当可见；允许显式补充或覆盖，并区分其来源。
- 多通道预览应展示当前文件全部通道；不需要跨文件三分量组装界面。

### P8. 先建立可靠闭环，再逐步增加格式

- 首先形成“读取 → 解析 → 校验 → 单通道写出 → 重新读取验证”的可运行闭环，再逐步增加标准格式。
- 添加格式时优先重用公共解析、单位、时间、校验和诊断能力；避免为每种格式复制整套处理代码。
- 每增加一种重要格式，选用少量**真实样本**验证常见路径和一个关键边界情况；重点是正确性，不追求大量重复测试。
- 不以扩展格式为理由引入插件动态加载、复杂工作流、持久化任务系统等不必要的基础设施。

## 4. 基础概念与数据约定

| 概念 | 约定 |
|---|---|
| `FileData` | 一次解析一个文件所得结果，包含多条 Trace 及可选文件级元数据 |
| `Trace` | 单通道、独立属性、独立样本数组；方向与名称允许未知 |
| 采样间隔 `dt` | 等间隔时程的秒/样本；未知允许留空，不凭样本数推断 |
| 样本数 `N` | 由 `samples.size()` 确定；头段声明值单独用于核验 |
| 时间轴 | 等间隔时刻 `t_i=t_0+i·dt`；缺少绝对时刻时使用相对时间，不虚构日历时刻 |
| 时长 | 首末样本跨度 `(N-1)dt`，名义记录长度 `Ndt`；界面和导出必须明确语义 |
| 物理量 | 至少区分未知、加速度、速度、位移、原始数字计数 |
| 单位 | 首先完整支持加速度三种预设，未知值不执行换算；其他物理量按需求扩展 |
| 数据分段 | 对不连续波形不得默默补零或拼接；首期可拆成独立 Trace 或明确报不支持，并给出诊断 |
| 非等间隔时间 | 首期重点是等间隔记录；非等间隔输入不得强行平均成 `dt` |
| 元数据 | 核心字段 + 文件/Trace 级扩展属性；原格式不能表示的字段不伪造 |

## 5. 建议的技术结构

```text
Input file bytes
      │
      ▼
Format detection / explicit selection
      │
      ├── Binary readers (SAC, miniSEED, ...)
      └── Text header rules + shared text parser
      │
      ▼
FileData { Trace 1, Trace 2, ... }
      │
      ├── GUI: metadata + text preview + all trace plots
      └── CLI: info / convert / formats
      │
      ▼
Per-Trace validation & unit conversion when necessary
      │
      ▼
Writer(Trace) → one file per Trace
```

技术建议：核心处理与接口使用 C++，GUI 使用 Qt，CLI 与 GUI 调用同一核心服务；对于 miniSEED、SAC 等格式优先评估成熟库并确认许可。代码划分应与真实功能规模匹配，不为未来可能出现的需求预设大型框架。

## 6. 分阶段方向

1. **第一阶段：基础转换闭环。** 核心模型、统一文本解析、首批标准格式、CLI 与最小 GUI、单通道导出、实际样本校验。
2. **后续阶段：扩展格式与适配能力。** COSMOS/SMC、K-NET、国内 UA、专有 miniSEED/仪器格式、复杂文本布局等，依据样本与需求逐步实现。
3. **后续阶段：批量转换与高级预览。** 目录独立批量处理、解析配置复用、转换日志与失败汇总、频谱及基础地震动指标。
4. **更远期：选定的信号处理能力。** 按实际需求逐步添加；不以完整复刻 SeismoSignal、REST 为目标。

上述顺序是功能演进方向，不是必须依次建立四个大型版本。

## 7. 变更原则

- 若新格式无法适配，应优先确认是**表头解释、数据布局、时间表达还是物理标定**问题；不能轻易修改核心数据模型。
- 若确实需要拓展核心模型（例如显式非等间隔时间轴），需说明现有模型不足之处、向后兼容影响及最小修改方案。
- 若需求要求跨文件合并、多通道写入、自动信号处理等，应作为新的独立功能提案评估，而非在格式适配过程中顺手引入。
- 本文件作为项目约束基线；具体开发范围、任务分工和验收见 GMTools 第一阶段开发文档。
